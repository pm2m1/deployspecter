## Minimization (step 6)

Our replay and minimizer work on the core engine's serial schedules. They don't apply to coordinated saq runs.
Here the choice was between two actors only (`producer`, `worker`), and the worker is gated until every job is
enqueued, so the outcome didn't depend on the seed. Each workload's five seeds gave the same verdict and the same
grant count.

I minimized the workload instead, over the integration's whole grid with concurrency 2. **The smallest failing
workload is 3 jobs, concurrency 2, `max_burst_jobs` 2**: 80 grants, 3 jobs complete. Its trace is in
`forced_trace_conc2_cap2_jobs3.txt`:

1. One dequeue claims 2 jobs (grant 28).
2. Both finish (grants 56 and 60).
3. After the **first** finish the count is 1 of 2, so a new process task starts, and it claims the third job
   (grant 64).
4. The third job runs to completion (grant 77).

## Standalone reproduction (step 7): `standalone/`

Plain Python with saq's public API, against PostgreSQL 16 from `docker-compose.yml`: saq 0.26.5 from PyPI,
psycopg 3.3.9, Python 3.12.16 (`versions.txt`). It doesn't use DeploySpecter, and no coordinator forces the
interleaving. It ran 20 iterations per configuration, each on a fresh database:

| Configuration | Over the cap |
|---|---|
| concurrency 2, `max_burst_jobs` 2, 3 jobs | **20 of 20** (3 distinct jobs handled, all COMPLETE) |
| concurrency 2, `max_burst_jobs` 3, 4 jobs | **20 of 20** (4 distinct jobs) |
| control: concurrency 1, `max_burst_jobs` 2, 3 jobs | 0 of 20 (2 COMPLETE, 1 QUEUED) |
| control: concurrency 2, `max_burst_jobs` 2, 2 jobs | 0 of 20 |

saq logs "Some tasks did not finish within the shutdown grace period, requesting cancellation" once per iteration
in every configuration, the controls included. It matches the default `shutdown_grace_period_s` of `None`, which
gives a 0 s wait before upkeep tasks are cancelled. It doesn't depend on the cap, and no job status was affected.

The 0.1 s handler sleep keeps both slots busy at once. It is a property of this script, not a production frequency.

**Script error, corrected and recorded:** an earlier version named queues by the process id. That id is the same
in every container, so a later `docker compose run` on the same database picked up jobs left queued by an earlier
run. Its cap-3 output (4 handler calls, one job `QUEUED`) was therefore contaminated. The script now uses a random
run id, every configuration was re-run on a fresh database, and the contaminated output was discarded. A debug
re-run on a fresh database showed 4 distinct jobs handled, all `COMPLETE` with `attempts=1`, after a further 3 s.

## Verdict

The overrun reproduces on the latest release, without DeploySpecter, every time, whenever `concurrency > 1` and the
queue holds more jobs than `max_burst_jobs`. Whether it is a **defect or a docs gap** depends on intent: see
`SEMANTICS.md` and `UPSTREAM_ISSUE_saq.md`. It is not confirmed by a maintainer.
