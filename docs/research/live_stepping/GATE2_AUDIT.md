# Gate 2 audit: batches, scheduler limits and the LangGraph plan

Review only. No integration code exists yet, and the prototype still refuses `executemany` and pipeline mode. Measurements are in `evidence/gate2_audit.json`, regenerated by `tools/live_stepping_gate2_audit.py` on a disposable PostgreSQL 16 database with synthetic data. No LangGraph code was executed, and no held-out application was touched.

**Versions read:** psycopg 3.3.6 (libpq 18.6), and `langgraph-checkpoint-postgres` 3.2.0 at `d4149cc1f5384364d1a21092b4c2f582a6e7af8f`, whose lock file also pins psycopg 3.3.6.

## 1. What `executemany` really does

With libpq pipeline support, `Cursor.executemany` opens an internal pipeline, sends every parameter set without waiting for results, and syncs at the end. Internally it doesn't call the public `pipeline()` or `execute()`, so the prototype's overrides of those never see it. All its traffic does pass through `Connection.wait`.

### Measured against repeated `execute`

44 cells: 11 cases in each of 4 connection modes. Each cell compared committed state, exception, transaction status, row count and returned data.

| Mode | Committed state | Exception | Row count | Returned data |
|---|---|---|---|---|
| Autocommit, no transaction | **Differs on server errors** | Same | Last vs total | Same |
| Inside `conn.transaction()` | Same in all 11 | Same | Last vs total | Same |
| Not autocommit, then `commit()` | Same in all 11 | Same | Last vs total | Same |

**Autocommit is the trap.** All statements up to the pipeline's sync form one implicit transaction:

| Case (autocommit) | `executemany` rows committed | Repeated `execute` rows committed |
|---|---|---|
| Unique conflict on row 2 of 3 | None | Row 1 |
| Check failure on row 3 of 3 | None | Rows 1 and 2 |
| **Unadaptable parameter on row 2 (client-side)** | **Row 1** | Row 1 |
| **Application iterator raises after row 1** | **Row 1** | Row 1 |

So `executemany` under autocommit isn't simply atomic either. A server error rolls everything back, but a client-side error leaves earlier rows committed.

**Other measured differences:**

- While blocked on row 2 under autocommit, `executemany` holds row 1 locked and invisible to others. Repeated `execute` has already committed it: others read 5 instead of 0, and can lock it.
- `rowcount` is the total for a batch, and the last statement's for repeated calls. Summing matched in every case where no exception was raised and no results were collected.
- An empty sequence differs: row count 0 vs -1. On a non-autocommit connection, `executemany([])` also leaves a transaction open (`INTRANS` vs `IDLE`).
- Results collected with `returning=True` matched, but only through the `nextset` protocol, which a repeated-`execute` wrapper would have to imitate.
- Row count isn't meaningful inside a `conn.pipeline()` block until sync. It reads 0 or 1 for a batch and -1 for an `execute`.

### Internal interleaving is real

In plain psycopg with no instrumentation, inside an explicit transaction, a commit from another session landed between two statements of one `executemany`. The result was a torn row pair, `[0, 1]`. An opaque step can't reach this state.

## 2. Options A and B

Both were tried as scratch cursor classes in the audit script. Neither is in the prototype.

| | A: one opaque checkpoint | B: one step per parameter set |
|---|---|---|
| Autocommit | **Sound, but opaque.** A reader sees `[0,0]` or `[5,5]` only | **Wrong.** A reader sees `[5,0]`, which real `executemany` can't show on server-error-free paths. Must not be used |
| Explicit transaction | **Sound, but incomplete.** Never reaches the real torn state `[0,1]` | Reaches `[0,0]`, `[0,1]`, `[1,1]` in 5 interleavings, against A's 4 interleavings and 2 states |
| Lock waits | Blocked batch lets the holder finish; 50 of 50 exact replays | Inherited from `execute` |
| Trace | One record with no parameters, because a lazy iterator mustn't be consumed for logging | One record per statement |

**Classification:**

- **A is supportable, classified as `opaque_batch`, "internally uncontrolled".** It records no per-statement schedule and can't support a claim of complete coverage, as frozen protocol section 6 requires. One extra fail-closed rule is needed. The prototype's effect tracking infers outcomes from transaction status, and after a client-side error under autocommit that would say nothing committed when row 1 did. Any non-server error from an opaque batch under autocommit must therefore be recorded as `effect_unknown`, which makes the run inconclusive.
- **B is a candidate only for an explicit transaction, with `returning=False`, a non-empty sequence, and a summed row count.** The evidence is 22 synthetic cells in the two transactional modes. That's agreement on those cases, not a proof of equivalence, and it isn't independent validation, because I wrote both the cases and the wrapper. It stays refused until validated against PostgreSQL's server log and a case list written by someone else.
- **Outside those limits, it remains `unsupported`.**
- **`conn.pipeline()` as an application block remains `unsupported`.** It spans arbitrary Python, its results are deferred until sync, and no single gate can represent it.

**Replacing `executemany` with repeated `execute` is not transparent, and isn't justified for autocommit.**

## 3. Deadlock victims and lock wakeups

| Measurement | Idle | CPU load | Plain psycopg, no controller |
|---|---|---|---|
| Deadlock victim, 200 runs | `a` 189, `b` 11 | `a` 173, `b` 27 | `a` 143, `b` 57 |
| Four-actor wakeup order, 200 runs | `abcd` 143, `abdc` 57 | `abcd` 166, `abdc` 34 | `abcd` 168, `abdc` 32 |

**The variation exists without my controller, so it belongs to PostgreSQL.** The harness can't be blamed for it, and can't remove it. Following instructions, I'm not trying to force victims with `deadlock_timeout`, and I withdraw my earlier suggestion to test that.

**My earlier statement needs correcting.** I reported a three-actor chain matching in 100 of 100 replays as evidence of stability. Four actors show a 16% to 29% wakeup variation, and the final state changes with it. Three-actor stability doesn't generalize.

### Three kinds of reproduction

Strict replay of one recorded deadlock trace, with victim `a`, 200 attempts:

| Level | Reproduced |
|---|---|
| Outcome class (`deadlock`) | 200 of 200 |
| Committed final state | 193 of 200 |
| Exact trace | 193 of 200 |
| Same victim | 193 of 200 |

- The last three coincide exactly: **given the same victim, the trace and state reproduced every time.** Each scheduling run produced exactly two exact traces, one per victim.
- Divergence never appeared, because the decisions stay legal for either victim. **A strict replay reaching the end isn't evidence that it reproduced.** Only the fingerprint comparison shows that.
- In this scenario the victim decides the final state (`[10,10]` or `[20,20]`), so semantic reproduction fails along with exact reproduction.

### Consequence for the frozen protocol

Protocol section 5 requires 3 of 3 semantic replays, including the same final state. In the worst measured rate, a state reached only with the rarer victim (`b`, 5.5% idle) would replay 3 of 3 about 0.02% of the time, so a real defect could be labelled unstable. **Amendment 002 (committed `801acd0`)** now conditions replay on the server's own choices, with one candidate and 125 attempts for every arm. The earlier draft's 30 attempts was too few: it reaches 3 comparable attempts only 18.8% of the time for a 5% outcome, against 95.2% for 125.

## 4. Other scheduler limits

| Area | Finding | Evidence | Severity |
|---|---|---|---|
| Own connection, **write** | **Run reports `completed`, while committed data was silently changed** (`c1 = 777`) | Measured | **Blocking** |
| Own connection, read; thread; `AsyncConnection`; subprocess | Run reports `completed` | Measured | **Blocking** |
| `conn.pgconn.exec_(...)` | Run reports `completed`. No Python-side guard sees it | Measured | **Blocking** |
| `psycopg.Connection.wait(conn, ...)` | Run reports `completed` | Measured | **Blocking** |
| `psycopg.Cursor(conn)` | Refused by the traffic guard | Measured | Handled |
| Raw access could also `RESET ROLE` | Actors log in as admin, then `SET ROLE`. A raw bypass could drop the restriction | From reading | **Blocking for external code** |
| Lock held by a session outside the run | Recorded as `external`, doesn't mark the run. An autovacuum wait could produce a false settle | From reading | Fix before Gate 2 |
| `sessions_left_open > 0` | Reported, but doesn't change the outcome | From reading | Fix before Gate 2 |
| Abort race | `cancel_safe` is sent once. If a granted statement hasn't reached the server yet, the cancel can be lost, and the actor waits through the grace period | From reading, not measured | Measure |
| Closing a stuck connection | The controller calls `conn.close()` while the actor's thread may still be inside `wait`. Behaviour isn't established | From reading, not measured | Measure |
| `Sandbox.reset` | `lock_timeout` is 0 on the admin session, so `DROP SCHEMA` can hang behind an outside lock. That module is frozen, so the fix must wrap it | From reading | Fix before Gate 2 |

Transaction ownership and cleanup held up in the existing tests: a connection is bound to one actor thread, an open transaction gets a scheduled rollback, and aborts never commit.

## 5. Recommended fail-closed connection registration

Client-side guards can't close this. Only server-side evidence caught every bypass.

| Scenario | Current outcome | Session counter | Server log reconciliation |
|---|---|---|---|
| Clean run | `completed` | Not flagged | Not flagged |
| Clean two-actor reservations | `completed` | Not measured | Not flagged |
| Own connection, read | `completed` | **Flagged** | **Flagged** |
| Own connection, write | `completed` | **Flagged** | **Flagged** |
| `AsyncConnection` | `completed` | **Flagged** | **Flagged** |
| New thread, new connection | `completed` | **Flagged** | **Flagged** |
| Subprocess | `completed` | **Flagged** | **Flagged** |
| Raw `pgconn.exec_` | `completed` | Missed | **Flagged** |
| Parent-class `wait` | `completed` | Missed | **Flagged** |

These are 9 runs, enough to show the mechanism but not to establish a false-flag rate. A soak test is part of the plan.

**The strategy, in order:**

1. **Restricted login role.** For external code, log in directly as a non-superuser role created for the run, with a random password and `CONNECTION LIMIT` equal to the actor count. The admin credential never exists in an actor's process. A surplus connection on that role is refused at connect time, and a raw bypass can't `RESET ROLE` to anything useful. `CONNECTION LIMIT` is defence in depth only: it doesn't see statements on a registered session, other roles, or a bypass within the limit.
2. **Injection only.** The harness creates all connections and hands over objects. It clears `DATABASE_URL` and `PG*` variables from the environment that application code can read. Nothing patches `psycopg` globally.
3. **Registry preflight.** Before a run, every connection in the target object must be a registered `SteppedConnection`. `ConnectionPool`, or a non-`None` `pipe`, is refused.
4. **Session counter per run.** The change in `pg_stat_database.sessions` must equal the actor count, or the run is `unsupported`.
5. **Server log reconciliation per run.** The dedicated disposable cluster runs with `log_connections` and `log_statement=all`. Any unknown session, unexpected statement or missing statement makes the run `unsupported`.
6. **Taint and discard.** A flagged run's final state is never scored. The next run rebuilds the schema.
7. **Canaries before evaluation.** All the bypasses above run as tests, and each must be flagged. If not, evaluation doesn't start.

Remaining gaps: reconciliation compares statement text and count, not parameter values, and code that reaches the database through a different database or server is out of its view.

## 6. LangGraph integration plan

No implementation has started.

### Compatibility of the pinned package, by reading

| Operation | Path | Verdict |
|---|---|---|
| Constructor | `isinstance(conn, Connection)` accepts the subclass; `conn.cursor(binary=True, row_factory=dict_row)` passes through | Compatible, untested |
| `get_tuple` | No pipeline. One `SELECT`, plus a second only for legacy checkpoints | Compatible, read-only |
| **`prune(strategy="delete")`** | No pipeline. `conn.transaction()` with three `DELETE`s | **Compatible, writes in an explicit transaction** |
| `put`, `put_writes`, `delete_thread` | `conn.pipeline()` by default, plus `executemany` in `put` and `put_writes` | **Refused** |
| `setup` | DDL and `CREATE INDEX CONCURRENTLY`, which can't run in `Sandbox.reset`'s transaction or under the actor role | Harness only, uninstrumented |
| `supports_pipeline = False` | Not used. Measured as not equivalent: on client-side errors the default commits earlier rows and the fallback commits none | Rejected as a substitute |

### First operation: `PostgresSaver.prune(thread_ids, strategy="delete")`

It's the smallest default path that writes. It has a real multi-statement transaction, needs no pipeline or `executemany`, and has committed state to compare. `get_tuple` is the second actor, as an observer.

**This doesn't cover `put`.** Passing Gate 2 on this operation says nothing about checkpoint writes, and the report must state that.

### Steps

1. **Guards first.** Implement section 5 and the fixes marked "before Gate 2", with canary tests, using only existing synthetic apps.
2. **Dependency.** Don't change `pyproject.toml` or `uv.lock` on anything bound for `main`. Use an isolated research environment with exact pins: `langgraph-checkpoint-postgres==3.2.0`, `langgraph-checkpoint==4.3.0`, `psycopg==3.3.6`, `psycopg-pool==3.3.3`. Tests skip when it's absent.
3. **Provenance.** Check that the installed package's files match tag commit `d4149cc` before any run. A mismatch stops the work.
4. **Harness bootstrap.** Rebuild `ds_run` and call `setup()` on a plain admin connection. Seed through plain `put()` with fixed synthetic thread and checkpoint ids and timestamps, then re-grant the actor role, because `Sandbox.reset`'s grants run before these tables exist.
5. **Actors.** One `PostgresSaver` per actor, with one registered autocommit connection and no pipe.

### Stop conditions

- Any difference in test 4 or 6 stops the work, and it gets reported rather than adapted around.
- An unexpected refusal is recorded as a compatibility finding. The tool isn't widened to pass it without a separate decision.
- A plausible problem in LangGraph itself falls under protocol section 13: stop, keep it confidential, and report it privately only on your decision.
