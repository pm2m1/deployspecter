PostgreSQL deployment testing

Your migration passes every test. Then a backfill erases a user's update.

During a rollout, old code, new code and background jobs share one database. DeploySpecter runs them through real PostgreSQL interleavings, checks the outcome against independent requirements, and saves every failure so you can replay it.

The hazard

Each release is correct. Together they can lose data.

Rolling deployments keep several versions of your code on one schema for minutes or hours. Failures appear only when their operations land in a particular order, or when a migration meets data its authors didn't picture.

Stale writes

A job reads a row, a user changes it, and the job's later write puts back the old value.

Whole-record saves

The old release loads a record and saves every column, undoing a change the new release just made.

Migration logic

Some defects need no race at all. A sync trigger can be wrong in a single transaction, once real data has the right shape.

How it works

From source code to a failure you can replay

  1. Extract operations

    Parses the code without running it, and lists its SQL statements, transactions and data flow.

    Static analysis

  2. Propose tests

    Muse Spark, a non-LLM generator or a person writes a test: actors, inputs and starting rows.

    Muse Spark or non-AI generator

  3. Validate

    Rejects anything unsupported. A test can't contain SQL, and only names statements in your code.

    Rule-based validator

  4. Execute interleavings

    Runs legal orderings on PostgreSQL, one session per actor, within schedule and time budgets.

    Real PostgreSQL

  5. Check independently

    A hand-written oracle compares what committed with the final state. It alone produces findings.

    Independent oracle

  6. Minimize and replay

    Shrinks the failure, saves it, and re-executes it to confirm that behaviour is identical.

    Real PostgreSQL

Meta Muse Spark

The model proposes tests. It doesn't decide what's true.

Muse Spark reads the source, the extracted statements and the schema, then proposes application-aware tests and candidate invariants. It never sees scenario names, requirements or schedules.

  • Its output is data, so it can't carry SQL or code.
  • Its invariants are hypotheses, and can't produce a finding.

Real-world example

A defect GitLab published, reproduced in a minimal fixture

GitLab documented a sync trigger that removed a user's destination row when one access level was deleted, even though another remained. This independently written fixture models that behaviour. It isn't GitLab's schema or workload.

This defect needs no concurrency: it fails in a single transaction, so it's a migration semantics defect. The stale backfill above is the opposite: no serial order fails.

      Limitations

      • A small benchmark, designed together with its oracles and baselines, so scores are optimistic and don't generalize.
      • Requirements are written by hand per scenario.
      • Scheduling stops at statement boundaries, and extraction covers limited Python and SQL patterns.
      • This isn't a production-safety guarantee, and it can't analyze arbitrary repositories.

      Architecture

      Small, separated components

      Source extraction

      Reads Python with ast, without importing or running it.

      Test proposals

      One declarative format for every generator, with no SQL field.

      Validator

      The trust boundary between generated specs and execution.

      Scheduler and explorer

      One session per actor. Lock waits come from pg_blocking_pids.

      Oracle

      Reference models over committed history, hidden from generators.

      Replay and minimizer

      Self-contained artifacts, with every reduction re-executed.

      Disposable database

      A dedicated test database, a non-superuser role, and a rebuilt schema per schedule.

      Model client

      Off by default, with hard request and spending limits and no retries.
